核心概念通信协议帧结构

直接使用串口发送固件数据，就像用卡车运送一堆散装的砖头。你不知道这车砖头是给谁的，也不知道总数是多少，更不知道路上有没有丢失几块。串口通信协议，就是为这些“砖头”贴上标签、打好包装、附上清单，确保它们能完整、准确地送达目的地。

通信协议：通信双方预先约定好的一套数据组织与交互规则。它定义了数据包的格式、含义以及处理流程，是确保通信可靠性的基础。

为什么需要自定义协议？

STM32的UART外设本身只负责比特流的收发，它不关心数据内容。如果没有协议，上位机发送的固件数据流一旦出现一个字节的错误、丢失或顺序错乱，Bootloader将无法察觉，最终导致升级失败甚至系统崩溃。

我在一个早期项目中踩过这个坑，当时只是简单地将串口接收到的数据直接写入Flash，结果有大约5%的概率升级后程序跑飞。后来发现是车间电磁干扰导致串口偶尔错位一个字节。引入协议后，这个问题被彻底解决。

一个实用的Bootloader协议帧结构

对于STM32 Bootloader，我们不需要像Modbus那样复杂的协议。一个包含帧头、命令、长度、数据和校验的帧结构就能满足绝大多数需求。下面是一个经过多个项目验证的可靠设计。

字段字节数说明示例值（十六进制）
帧头 (Header)2固定值，用于帧起始同步0xAA, 0x55
命令字 (CMD)1标识本帧的意图0x01 (连接)，0x02 (数据)
数据长度 (Len)2后续“数据载荷”的字节数0x00, 0x80 (128字节)
数据载荷 (Data)N (由Len决定)实际要传输的信息，如固件数据…
校验和 (Checksum)1从CMD到Data所有字节的累加和（取低8位）…

这个结构非常关键。帧头帮助接收方从连续的字节流中准确切分出每一帧的开始。命令字告诉Bootloader这帧数据是用来做什么的。长度字段让接收方知道该收多少数据才算完整一帧。校验和则是数据的“指纹”，用于验证传输过程中数据是否被篡改或丢失。

关键点：校验和的选择

累加和校验（Checksum）计算简单，资源消耗低，适合STM32这类MCU，能有效检测单字节错误和多数多字节错误。对于安全性要求极高的场景，可以考虑CRC16，但其计算量会大一些。实际开发中，大部分团队在串口Bootloader中会选择累加和，因为它够用且高效。

协议命令集设计

协议需要定义一套简单的“对话”指令。Bootloader作为“应答方”，需要响应上位机的各种请求。以下是几个最核心的命令。

连接握手 (CMD: 0x01)

  • 上位机发送：帧头 + 0x01 + 长度0 + 校验和
  • Bootloader回复：成功返回ACK(0x00)，失败返回NAK(错误码)
  • 目的：探测Bootloader是否存在并准备就绪

获取信息 (CMD: 0x02)

  • 上位机发送：命令帧
  • Bootloader回复：包含芯片ID、Flash大小、Bootloader版本等信息的帧
  • 目的：让上位机识别设备并决定后续操作

数据写入 (CMD: 0x03)

  • 上位机发送：帧头 + 0x03 + 长度 + (地址+数据) + 校验和
  • Bootloader回复：写入成功返回ACK，失败返回NAK
  • 目的：传输固件数据块的核心命令

跳转执行 (CMD: 0x04)

  • 上位机发送：命令帧
  • Bootloader回复：ACK后执行跳转
  • 目的：完成升级，启动新固件

这里有个隐藏的坑：数据写入命令（0x03）的数据载荷，通常前4个字节是32位的Flash起始地址，后面才是真正的固件数据。所以“数据长度”字段的值应该是“4 + 实际数据长度”。

编者提示：在设计命令字时，最好将ACK(确认)和NAK(否认)的回复也标准化。例如，规定回复帧的命令字为原命令字最高位置1（0x81代表对0x01的回复），数据域的第一个字节为状态（0x00成功，其他为错误码）。这样上位机解析逻辑会更清晰统一。

协议处理流程：Bootloader侧的状态机

Bootloader的串口中断服务函数不能简单地将收到的每个字节存入缓冲区。它需要像一个“流水线质检员”，按照协议规则一步步检查、组装。这个过程最适合用状态机来实现。

状态：等待帧头
→
收到0xAA?
→
状态：检查帧头2
→
收到0x55?
状态：接收命令
→
状态：接收长度高字节
→
状态：接收长度低字节
→
状态：接收数据
→
状态：接收校验和

状态机从“等待帧头”开始。只有连续收到0xAA和0x55，才认为一帧开始，进入接收命令的状态。随后依次接收长度、数据（根据长度值循环接收），最后接收校验和。在“接收校验和”状态完成后，立即计算校验并判断帧的有效性。

如果任何一步收到的字节不符合预期（比如在等帧头时收到了其他值），状态机都应重置回“等待帧头”，丢弃无效数据。这是协议健壮性的关键。

// 状态机枚举定义示例
typedef enum {
  STATE_WAIT_HEADER1,
  STATE_WAIT_HEADER2,
  STATE_WAIT_CMD,
  STATE_WAIT_LEN_H,
  STATE_WAIT_LEN_L,
  STATE_WAIT_DATA,
  STATE_WAIT_CHECKSUM
} uart_parser_state_t;

// 在串口中断服务函数(ISR)中的简化处理逻辑
void USART1_IRQHandler(void) {
  uint8_t rx_byte = USART1->RDR; // 读取接收到的字节
  static uart_parser_state_t state = STATE_WAIT_HEADER1;
  static uint16_t data_index = 0;
  static uint16_t expected_len = 0;

  switch(state) {
    case STATE_WAIT_HEADER1:
      if (rx_byte == 0xAA) state = STATE_WAIT_HEADER2;
      break;
    case STATE_WAIT_HEADER2:
      if (rx_byte == 0x55) state = STATE_WAIT_CMD;
      else state = STATE_WAIT_HEADER1; // 同步失败，重置
      break;
    case STATE_WAIT_CMD:
      current_frame.cmd = rx_byte;
      state = STATE_WAIT_LEN_H;
      break;
    // ... 其他状态处理（接收长度、数据等）
    case STATE_WAIT_CHECKSUM:
      current_frame.checksum = rx_byte;
      // 帧接收完成，可以置位标志位，在主循环中处理
      frame_received_flag = 1;
      state = STATE_WAIT_HEADER1; // 重置状态机，等待下一帧
      break;
  }
}

常见误区

  • 在中断中做复杂处理：串口ISR里只应完成字节接收和状态切换，完整的校验计算、命令解析和应答应在主循环中根据frame_received_flag标志进行。长时间阻塞ISR会导致数据丢失。
  • 忽略超时机制：如果一帧数据没传完就中断了，状态机会一直等待。必须加入超时判断（例如，10ms内未收到任何字节则重置状态机），防止“卡死”。
  • 校验范围错误：计算校验和时，必须从命令字（CMD）开始，一直累加到数据载荷的最后一个字节。帧头（0xAA, 0x55）不参与校验，因为它们只用于同步。

上位机与Bootloader的交互时序

一次成功的固件升级，是上位机和Bootloader之间多次“一问一答”的配合。理解这个时序对于调试至关重要。

上位机：发送连接命令(0x01)
→
Bootloader：回复ACK
→
上位机：发送数据帧(0x03)
→
Bootloader：回复ACK

... 重复发送数据帧 ...

上位机：发送跳转命令(0x04)
→
Bootloader：回复ACK并跳转

这里有个实际开发中的经验：上位机在发送下一帧数据或命令前，必须等待并收到Bootloader对上一帧的ACK回复。这种“停-等”协议虽然效率不是最高，但最简单可靠，能确保每一帧数据都落地后再发下一帧。如果你看到上位机一直发送但Bootloader没反应，大概率是某一帧数据校验失败，Bootloader回复了NAK，但上位机没有处理这个错误回复，还在自顾自地发送。

波特率选择115200是常见平衡点。对于STM32F1/F4系列，使用USART1（PA9/PA10）或USART2（PA2/PA3）均可。务必确保Bootloader和上位机使用相同的波特率、数据位（8）、停止位（1）和奇偶校验位（无）。

动手试一试

1. 定义你的协议帧结构：打开STM32CubeIDE，创建一个头文件（如bootloader_protocol.h），用C语言结构体定义你的协议帧。包含帧头、命令、长度、数据数组和校验和字段。
2. 实现校验和函数：编写一个函数uint8_t calculate_checksum(const uint8_t* data, uint16_t len)，计算从指定地址开始、指定长度的数据的累加和。
3. 模拟解析：在PC上用一个简单的串口调试工具（或Python脚本），手动组织一个符合你协议格式的数据帧（例如，连接命令帧），发送给开发板，观察Bootloader的回复（可以通过一个LED闪烁来指示收到正确帧）。

本章小结

  • 裸串口通信不可靠，必须依赖自定义协议来保证数据传输的完整性和正确性。
  • 一个基础的协议帧应包含帧头（同步）、命令（意图）、长度（数据量）、数据（有效信息）和校验和（检错）五个部分。
  • 使用状态机模型在Bootloader侧解析协议是标准且可靠的方法，状态机应在串口中断中驱动，在主循环中处理完整帧。
  • 设计简单的命令集（连接、获取信息、写数据、跳转）并遵循“一问一答”的交互时序，是实现稳定升级流程的关键。
  • 累加和校验在资源与可靠性间取得了良好平衡，是STM32 Bootloader协议的常用选择。
