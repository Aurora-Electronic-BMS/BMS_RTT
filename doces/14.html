核心概念看门狗定时器Flash写保护

一个没有保护机制的Bootloader，就像一辆没有安全气囊和ABS的汽车，在平坦道路上或许能开，但一旦遇到意外（程序跑飞、电磁干扰、电源毛刺），系统就可能彻底“趴窝”，失去通过再次上电恢复的能力。我在一个车载ECU项目中就踩过这个坑，早期版本忽略了看门狗，产线测试时偶尔会因为强电磁干扰导致Bootloader卡死，整块板子只能返厂用JTAG救砖，损失惨重。

生活类比： 看门狗就像你家里的智能宠物喂食器，你必须每隔一段时间（比如12小时）去按一下“确认”按钮。如果你一切正常，按时去按，系统就认为你“活着”。如果你生病昏迷了，一直没去按，喂食器就会判定你出了意外，自动执行预设的应急方案——比如给家人发警报。在单片机里，这个“按按钮”就是程序定期“喂狗”，应急方案就是系统复位。

技术定义： 看门狗定时器（Watchdog Timer, WDT）是一个独立的硬件计数器，启用后开始倒计时。程序必须在其超时前通过写特定寄存器来“刷新”计数器（俗称“喂狗”）。如果程序因故障（死循环、跑飞）未能及时喂狗，看门狗超时就会触发系统复位，让设备从异常状态中恢复。

STM32的两种看门狗：IWDG与WWDG

STM32提供了两种内置的看门狗，它们的原理和适用场景截然不同。选择错误，保护效果会大打折扣。

特性独立看门狗 (IWDG)窗口看门狗 (WWDG)
时钟源独立的低速内部时钟 (LSI，~32kHz)APB1总线时钟 (PCLK1)

Bootloader推荐度高（核心保护）中（辅助保护）

对于Bootloader，独立看门狗(IWDG)是必须的。因为它基于独立的LSI时钟，即使主时钟（HSE/HSI）出问题导致程序“跑飞”，IWDG依然能正常工作并触发复位。实际开发中，大部分高可靠性项目都会在Bootloader启动后立即初始化并启用IWDG。

关键点：为什么Bootloader特别需要IWDG？

Bootloader运行期间可能进行耗时的Flash擦写操作（例如，擦除一个64KB的扇区可能需要几十到上百毫秒）。如果在这个过程中系统受到干扰，程序计数器(PC)跳转到未知地址，整个升级流程就会卡死，设备“变砖”。启用IWDG后，只要这个“卡死”时间超过看门狗超时时间（例如1秒），系统就会自动复位，Bootloader重新开始运行，设备仍有恢复的可能。

在Bootloader中集成独立看门狗(IWDG)

使用STM32 HAL库配置IWDG非常直接。关键是要规划好喂狗的位置，确保在正常执行流中能定期刷新。

// 在Bootloader的main函数初始化阶段启用IWDG
void IWDG_Init(void) {
    // 1. 启用IWDG时钟（LSI通常已由启动代码开启）
    // 2. 配置预分频器和重载值，决定超时时间
    //    以LSI=32kHz，预分频64，重载值500为例：
    //    超时时间 = (64 * 500) / 32000 ≈ 1秒
    hiwdg.Instance = IWDG;
    hiwdg.Init.Prescaler = IWDG_PRESCALER_64; // 预分频
    hiwdg.Init.Reload = 500;                 // 重载值
    if (HAL_IWDG_Init(&hiwdg) != HAL_OK) {
        // 初始化错误处理，例如点亮错误LED
        Error_Handler();
    }
    // 初始化后，IWDG已经开始递减计数
}

// 喂狗函数，需要在主循环或关键任务中定期调用
void IWDG_Refresh(void) {
    HAL_IWDG_Refresh(&hiwdg);
}

这里有个隐藏的坑：Flash擦写期间无法喂狗。像STM32F4系列，擦除一个大扇区可能需要上百毫秒。如果你的IWDG超时时间设置得过短（比如200ms），可能在擦写还没完成时就触发复位了。我的经验是，根据芯片手册里Flash擦写的最长时间，将IWDG超时设置为该时间的2-3倍以上，并留足余量。

⚠️ 常见误区

  • 在中断服务程序(ISR)中喂狗： 这是危险的做法。即使主程序已卡死，定时器中断可能仍在运行，这会导致看门狗永远不被触发，失去保护意义。喂狗操作应放在主程序的任务调度或主循环中。
  • 超时时间设置过短： 没有考虑Flash操作、复杂校验等耗时任务的执行时间，导致正常操作下频繁意外复位。
  • 忘记在跳转前喂狗： 从Bootloader跳转到应用程序(App)前，必须喂一次狗。否则，IWDG可能在App初始化完成前就超时，导致系统不断复位，无法进入App。

Bootloader与应用程序的看门狗协作

一个完整的系统，Bootloader和App可能都需要看门狗保护。这里有两种主流策略：

策略一：独立管理

  • Bootloader和App各自初始化并启用自己的IWDG。
  • 在跳转App前，Bootloader喂一次狗，确保App有足够时间完成自身IWDG初始化。
  • App初始化时，重新配置IWDG参数（可选）。
  • 优点： 逻辑清晰，两者互不影响。

策略二：继承管理

  • Bootloader启用IWDG后，永不喂狗（或使用极长的超时时间）。
  • App启动后，承担起喂狗的责任。
  • 如果App跑飞，Bootloader启用着的IWDG最终会触发复位。
  • 优点： 确保只要Bootloader正常，系统总有复位手段。

我推荐策略一，因为它更灵活可靠。策略二有个问题：如果App非常复杂，初始化时间可能很长，Bootloader设置的超时时间可能不够用。采用策略一时，跳转代码可以这样写：

void JumpToApp(uint32_t app_address) {
    // ... 其他跳转准备（设置堆栈指针、关闭中断等） ...

    // 关键步骤：跳转前最后一次喂狗，为App争取初始化时间
    IWDG_Refresh();

    // 执行跳转
    void (*app_reset_handler)(void) = (void (*)(void)) *(volatile uint32_t*)(app_address + 4);
    app_reset_handler();
}

编者提示： 调试带看门狗的系统时，如果连接了调试器（如ST-Link），默认行为可能会冻结看门狗计数器，导致你无法观察到超时复位现象。在STM32CubeIDE中，你需要在调试配置的“Debugger”选项卡下，找到“Watchdog”设置，将其从默认的“Disable in debug”改为“Enable in debug”，这样看门狗在调试时也会正常工作，方便你排查喂狗逻辑的问题。

Flash写保护：防止固件被意外修改

看门狗解决了“程序跑飞”的问题，但还有一种风险：“数据被意外修改”。在Bootloader运行期间，如果因为严重的电源干扰或程序缺陷，导致PC指针跳转到了Flash写操作函数，但传入的地址参数是错误的，就可能会误擦写Bootloader自身或关键系统数据，造成永久性损坏。

生活类比： 这就像你家的保险箱，里面放着房产证和现金（Bootloader和关键数据）。你知道密码，可以正常打开存放东西（正常升级）。但写保护就像给保险箱加装了一个“防误触锁”，在你不打算操作它的时候（比如日常运行），即使不小心碰到了开关（程序跑飞），保险箱也不会打开，东西是安全的。

技术定义： STM32的Flash存储器提供了写保护选项位（RDP, Read Protection Level）。通过配置RDP级别，可以锁定整个Flash或部分扇区，防止通过调试接口（JTAG/SWD）或运行中的程序代码对其进行擦写操作。只有通过特定的系统复位或解除保护序列才能重新获得写权限。

对于Bootloader开发，我们主要关注扇区写保护。你可以将存放Bootloader代码的Flash扇区（例如STM32F4的Sector 0）设置为写保护，而将用于存储应用程序的扇区（如Sector 1-7）保持开放。

// 在Bootloader初始化时，保护自身所在的扇区（示例为Sector 0）
void Flash_EnableSectorProtection(void) {
    HAL_FLASH_OB_Unlock(); // 解锁选项字节编程
    FLASH_OBProgramInitTypeDef ob_config;
    ob_config.OptionType = OPTIONTYPE_WRP;        // 配置写保护
    ob_config.WRPState = OB_WRPSTATE_ENABLE;      // 使能保护
    ob_config.WRPSector = OB_WRP_SECTOR_0;        // 保护扇区0
    // 具体扇区掩码需根据芯片型号定义，请查阅对应HAL库头文件
    if (HAL_FLASHEx_OBProgram(&ob_config) != HAL_OK) {
        Error_Handler();
    }
    // 应用选项字节更改（这会触发系统复位）
    HAL_FLASH_OB_Launch();
    // 执行此函数后，芯片会复位，Bootloader重新运行，但扇区0已受保护
}

重要提示： 调用HAL_FLASH_OB_Launch()后，芯片会立即复位。因此，这段代码通常只在Bootloader第一次烧录后，或确认需要永久锁定Bootloader区时执行一次。在实际的IAP流程中，我们一般不会在每次升级时都操作写保护。

如果你看到在调用Flash编程函数后，芯片没有正确写入数据却返回成功，或者程序莫名其妙地复位，除了检查地址对齐和解锁序列，还要排查一下目标扇区是否被意外写保护了。使用STM32CubeProgrammer工具可以直观地查看和修改Flash的写保护状态。

动手试一试

在你的Bootloader工程中，添加独立看门狗(IWDG)功能。

  1. 在main.c的初始化部分（SystemClock_Config之后），调用HAL_IWDG_Init初始化看门狗，设置超时时间为2秒左右。
  2. 在主循环中，每次循环都调用HAL_IWDG_Refresh喂狗。
  3. 为了测试看门狗是否生效，可以在主循环中故意添加一个永久循环（如while(1);），然后给芯片上电。观察芯片是否会在2秒后自动复位（可以通过一个LED的闪烁模式来判断）。
  4. 进阶尝试： 模拟Flash擦写耗时：在某个升级步骤中，用一个for循环延时1.5秒，并在这段延时内不喂狗。如果你的看门狗超时时间也是1.5秒，系统应该复位。尝试调整超时时间（如改为3秒），确保它能覆盖这个“模拟擦写”过程。

检验你的理解

  1. 判断题：独立看门狗(IWDG)的时钟源来自系统主时钟(HCLK)，如果主时钟故障，看门狗也会失效。
  2. 选择题：在Bootloader跳转到应用程序(App)之前，关于看门狗的正确操作是：
    A. 不需要做任何操作，App会自己处理。
    B. 应该先禁用看门狗，再跳转。
    C. 应该先喂一次狗，再跳转，为App初始化争取时间。
    D. 将看门狗的超时时间设置为无穷大。
  3. 判断题：Flash写保护功能一旦开启，就无法再通过程序代码解除，只能通过调试器擦除整个芯片。

本章小结

  • 独立看门狗(IWDG)基于独立时钟源，是Bootloader防止死锁、跑飞的核心保护机制，必须合理设置超时时间以覆盖Flash操作等耗时任务。
  • 窗口看门狗(WWDG)提供更严格的程序时序监控，可作为IWDG的补充，但在Bootloader中非必需。
  • Bootloader与应用程序应协同管理看门狗，推荐各自独立初始化和喂狗，并在跳转前喂狗以确保平稳过渡。
  • 利用Flash扇区写保护可以防止程序异常时误擦写Bootloader自身或关键数据，提升系统抗干扰能力。
  • 调试带看门狗的系统时，需注意调试器的配置，确保看门狗在调试模式下仍能正常工作以便观察现象。
