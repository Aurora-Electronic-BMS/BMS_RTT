核心概念内存映射分区规划

想象一下你的电脑硬盘，C盘装系统，D盘放软件，E盘存资料。STM32这颗芯片内部也有类似的“硬盘”和“内存”，程序和数据需要被合理地“分区”存放。理解这个布局，是设计Bootloader和应用程序升级方案的第一步。

什么是内存映射？

内存映射（Memory Map）是微控制器将内部所有功能单元（如Flash、RAM、外设寄存器）都统一编址到一个线性地址空间里的方案。对CPU而言，无论是读取程序指令，还是访问一个GPIO口的状态，都像是在访问一个巨大的“内存数组”，只是地址不同。这简化了CPU的访问方式。

STM32的地址空间全景

不同系列的STM32（如F1、F4、H7）地址空间设计有差异，但核心架构一致。我们以最常见的STM32F1系列（Cortex-M3内核）和STM32F4系列（Cortex-M4内核）为例，它们都遵循ARM Cortex-M内核定义的存储器映射框架。

这个架构图展示了STM32地址空间的几个关键区块。主Flash（0x0800 0000开始）是我们存放用户程序（包括Bootloader和App）的地方。SRAM（0x2000 0000开始）是程序运行时的“工作台”，用于存放变量和堆栈。外设区域（0x4000 0000开始）则映射了所有片上外设（如GPIO、USART、TIMER）的配置寄存器。

关键存储区域详解

对于Bootloader开发，我们需要重点关注以下几个区域：

地址范围名称用途Bootloader开发中的关注点
0x0000 0000 - 0x0007 FFFF启动区域 (Aliased)根据启动模式映射到不同物理存储器决定CPU上电后从哪里取第一条指令
0x0800 0000 - 0x080X FFFF主Flash (Main Flash)存放用户程序代码和常量数据Bootloader和App的“家”，需要分区规划
0x1FFF 0000 - 0x1FFF 77FF系统存储器 (System Memory)出厂预置的Bootloader（如USART DFU）芯片自带的升级能力，通常我们不用它
0x2000 0000 - 0x2000 XXXXSRAM运行时的变量、堆栈、堆Bootloader和App运行时不能互相覆盖数据
0x4000 0000 - 0x5003 FFFF外设寄存器 (AHB/APB)配置和控制所有片上外设Bootloader和App使用外设前需重新初始化

启动区域的“别名”机制

地址0x0000 0000开始的区域是一个“别名窗口”，它本身没有物理存储器。CPU上电后从这里取第一条指令时，这个地址会根据芯片的启动引脚（BOOT0/BOOT1）设置，被硬件自动映射到三个物理位置之一：主Flash、系统存储器或内置SRAM。这个机制决定了芯片的启动模式。

Flash存储器的特性与限制

Flash是我们存放程序的地方，理解它的特性对安全编程至关重要。

⚠️ Flash操作常见误区

  • 不能按字节擦除：Flash的最小擦除单位是“扇区”（Sector）或“页”（Page），大小从1KB到128KB不等。擦除操作会将整个扇区所有位变为1（0xFF）。
  • 写操作只能将1变为0：编程（写入）操作只能将存储单元的位从1（擦除后状态）改为0。如果想将0改回1，必须执行擦除整个扇区的操作。
  • 运行时写自身需谨慎：当CPU从Flash执行指令时，对同一块Flash进行擦写操作可能导致总线冲突或读取错误。实际项目中，我们通常将擦写Flash的代码搬到SRAM中执行。

以STM32F103C8T6（中容量）为例，它的主Flash容量为64KB，被划分为若干页：

编者提示： 在项目初期，务必从芯片数据手册（Datasheet）和参考手册中确认Flash的准确容量和扇区划分。我曾在一个项目中，误将F407的扇区大小记成统一的128KB，导致擦除操作覆盖了不该碰的区域，系统直接卡死。不同容量、不同系列的STM32，Flash结构可能不同。

为Bootloader和App规划内存分区

内存分区，就是给Bootloader和应用程序在Flash和RAM中划出各自的“地盘”，确保它们互不干扰。这是IAP设计的核心。

典型分区方案

  • Bootloader区：固定放在Flash起始位置（如0x0800 0000），大小8-16KB通常足够。
  • 应用程序(App)区：紧接Bootloader之后存放（如0x0800 4000）。
  • 参数存储区：利用Flash最后一两个扇区，存放升级标志、版本号等。

SRAM分区考虑

  • Bootloader和App使用独立的堆栈空间。
  • 如果Bootloader需要大缓存接收固件，可预留一块固定RAM区域。
  • App跳转前，Bootloader应清理自己用过的全局变量区域。

地址映射关键点

  • App的编译链接地址必须与它在Flash中的物理分区地址一致。
  • 中断向量表的位置：Bootloader运行时有自己的向量表，跳转到App后，需要将向量表重定位到App区的起始地址。

下面是一个针对STM32F103C8T6（64KB Flash, 20KB RAM）的具体分区示例：

功能模块起始地址大小说明
Bootloader0x0800 00008KB (页0-页7)存放升级程序，固定不变
应用程序 (App)0x0800 200056KB (页8-页63)用户功能程序，可被新固件覆盖
App备份/参数区0x0800 FC001KB (页63)存放升级标志、CRC校验值等
Bootloader栈0x2000 00001KBBootloader专用栈空间
App栈/堆0x2000 040019KB应用程序使用的RAM区域

在这个方案中，Bootloader占据了Flash最开始的8KB。当我们需要升级App时，新的固件数据将通过通信接口（如串口）传给Bootloader，由Bootloader擦除从0x0800 2000开始的App区域，并将新程序写入。参数区（最后一页）因为独立且较小，可以用来安全地存储状态信息，避免在升级过程中被误擦除。

分区大小的经验法则

Bootloader分区大小不是拍脑袋决定的。你需要根据Bootloader要实现的功能（通信协议解析、Flash驱动、校验算法等）来估算代码量，并预留至少20%-30%的余量。一个只支持串口升级的简单Bootloader，在优化后8KB可能足够；但如果要支持以太网、加密、双备份等复杂功能，可能需要32KB甚至更多。务必在规划前，用编译器生成一个初步的代码大小报告。

链接脚本：将分区方案告诉编译器

分区方案最终需要在工程的链接脚本（Linker Script，通常是.ld文件）中体现。链接脚本决定了代码和数据被放置在Flash和RAM的哪个具体地址。

对于Bootloader工程，其链接脚本需要将代码定位到Flash起始区（如0x08000000）。对于App工程，则需要将代码定位到App分区起始地址（如0x08002000）。下面是一个App工程链接脚本关键部分的示意：

/* 定义存储器区域 */
MEMORY
{
  RAM (xrw)     : ORIGIN = 0x20000000, LENGTH = 20K
  FLASH (rx)    : ORIGIN = 0x08002000, LENGTH = 56K /* 注意起始地址！ */
}

/* 定义输出段 */
SECTIONS
{
  /* 中断向量表放在最前面 */
  .isr_vector : {
    . = ALIGN(4);
    KEEP(*(.isr_vector))
    . = ALIGN(4);
  } >FLASH

  /* 程序代码和常量紧随其后 */
  .text : {
    . = ALIGN(4);
    *(.text)
    *(.text*)
    . = ALIGN(4);
  } >FLASH
  ...
}

如果你使用STM32CubeIDE或Keil MDK，这些IDE提供了图形化或配置选项来设置程序的起始地址和大小，它们本质上也是在帮你修改链接脚本。

动手试一试

  1. 打开你手头STM32芯片的官方数据手册（Datasheet），找到“Memory mapping”章节，记录下主Flash、SRAM的起始地址和容量。
  2. 查阅参考手册（Reference Manual）的“Flash memory”章节，找到Flash的扇区划分表，记录下每个扇区的起始地址和大小。
  3. 基于你查到的信息，为你的芯片设计一个Bootloader分区方案。假设Bootloader需要12KB，请计算出App分区的起始地址和可用大小。

本章小结

  • 内存映射是将所有硬件资源统一编址的方案，CPU通过访问不同地址来操作Flash、RAM和外设。
  • STM32的Flash用于存储程序，擦除以扇区为单位，写操作只能将1变0；SRAM用于程序运行时数据。
  • 设计IAP必须规划内存分区，为Bootloader和App划分独立的Flash和RAM区域，避免相互冲突。
  • 分区方案需要在应用程序的链接脚本中体现，确保代码被链接到正确的物理地址。
  • 一切分区设计的基础是芯片的官方数据手册和参考手册，务必以手册为准。
