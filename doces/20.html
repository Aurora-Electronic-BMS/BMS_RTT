核心概念TFTPLwIP

想象一下，你不再需要拿着电脑和串口线跑到设备现场，只需在办公室点击鼠标，就能为成百上千台设备更新固件。这就是以太网升级带来的核心价值——远程、批量、高效。我在一个工业网关项目中，正是通过以太网IAP实现了对部署在全国各地设备的统一固件管理，将现场维护成本降低了80%。

生活类比： 就像用网盘下载一个大文件，你需要知道文件地址（服务器IP），确保网络通畅（链路层），然后启动下载工具（TFTP客户端），文件会被分成一个个小数据包传输，最后校验文件完整性。

技术定义： 通过以太网升级，是指Bootloader集成网络协议栈，作为一个网络客户端，从远程服务器（如TFTP服务器）获取固件文件，并将其写入内部Flash的过程。

以太网Bootloader的架构选择

实现网络升级，首先需要为Bootloader引入网络协议栈。在资源受限的MCU Bootloader中，我们通常选择轻量级的开源协议栈。

应用层 (TFTP Client)
↓
传输层 (UDP)
↓
网络层 (IP)
↓
链路层 (MAC+PHY)
↓
Flash编程
⇄
固件缓存
链路层和物理层由硬件（如STM32的ETH外设加LAN8720 PHY芯片）和底层驱动负责。网络层及以上，我们引入LwIP（Lightweight IP）协议栈。它是一个为嵌入式系统设计的开源TCP/IP协议栈，内存占用小，非常适合Bootloader环境。

关键决策：为什么用TFTP而不是HTTP？

TFTP（Trivial File Transfer Protocol）基于UDP，协议简单，代码实现量极小，没有复杂的连接管理和头部信息，非常适合在Bootloader中实现。HTTP基于TCP，虽然功能强大，但协议复杂，内存和代码开销大，在Bootloader中不是首选。

常见嵌入式网络协议栈对比（Bootloader视角）
协议栈协议支持内存占用代码大小Bootloader适用性
LwIPIP, ICMP, UDP, TCP (可选)~10-30 KB RAM~20-50 KB ROM高，模块化，可裁剪
uIPIP, ICMP, TCP极低小中，更古老，社区活跃度低
裸写UDP仅UDP（手动组包）最低最小低，需要处理所有底层细节，易出错

实际开发中，我强烈推荐使用LwIP的RAW API模式。它采用回调机制，避免了操作系统环境下复杂的线程同步问题，与Bootloader的单任务主循环模型完美契合。对于STM32，CubeMX可以直接生成LwIP的初始化代码和PHY驱动，大大降低了起步难度。

实现一个简单的TFTP客户端

TFTP协议非常简单，只有5种报文类型。在Bootloader中，我们只需要实现读取请求（RRQ）和数据块接收（DATA）。

初始化LwIP & 网络
→
发送RRQ包到服务器
→
循环接收DATA包
↓
校验块编号 & 写入缓存
→
回复ACK包
↺
↓
收到小于512B的包，传输结束
→
校验完整固件并写入Flash

TFTP数据包默认大小为512字节。每收到一个DATA包，客户端必须回复一个ACK确认包，服务器才会发送下一个包。这是TFTP实现可靠传输的基础。

下面是一个简化的TFTP客户端处理逻辑的核心代码片段。注意，在真实的LwIP RAW API中，网络报文的接收是在回调函数中处理的。

// TFTP操作码定义
#define TFTP_RRQ   1
#define TFTP_DATA  3
#define TFTP_ACK   4
#define TFTP_ERROR 5

// 全局状态
static uint16_t tftp_block_num = 0;
static struct udp_pcb *upcb = NULL;
static ip_addr_t server_ip;

// 发送RRQ请求
void tftp_send_rrq(const char *filename) {
    struct pbuf *p = pbuf_alloc(PBUF_TRANSPORT, 512, PBUF_RAM);
    char *payload = (char *)p->payload;
    uint16_t *opcode = (uint16_t *)payload;

    *opcode = htons(TFTP_RRQ);
    strcpy(payload + 2, filename); // 文件名，如“firmware.bin”
    strcpy(payload + 2 + strlen(filename) + 1, "octet"); // 模式

    udp_sendto(upcb, p, &server_ip, TFTP_SERVER_PORT);
    pbuf_free(p);
}

// UDP接收回调（LwIP RAW API）
static void tftp_recv_callback(void *arg, struct udp_pcb *pcb, struct pbuf *p,
                              const ip_addr_t *addr, u16_t port) {
    uint16_t *opcode = (uint16_t *)p->payload;
    uint16_t recv_opcode = ntohs(*opcode);

    if (recv_opcode == TFTP_DATA) {
        uint16_t recv_block = ntohs(*(uint16_t *)(p->payload + 2));
        if (recv_block == tftp_block_num + 1) {
            // 收到期望的数据块
            write_data_to_flash_buffer(p->payload + 4, p->len - 4);
            tftp_block_num = recv_block;
            tftp_send_ack(recv_block); // 发送ACK
            if (p->len < 516) { // 数据部分小于512B，传输结束
                finalize_firmware_update();
            }
        } else {
            // 收到重复或乱序的包，重发上一次的ACK
            tftp_send_ack(tftp_block_num);
        }
    }
    pbuf_free(p);
}

常见误区

  • 忽略网络字节序： TFTP协议中所有多字节字段（操作码、块编号）都使用大端字节序（网络字节序）。STM32是小端架构，必须使用htons()（主机到网络短整型）和ntohs()（网络到主机）进行转换，否则通信会完全失败。
  • ACK包丢失导致死锁： 如果客户端发出的ACK包丢失，服务器会等待超时后重发上一个DATA包。你的客户端必须能处理这种重复的DATA包，并重新回复ACK，否则升级过程会卡死。上面的代码通过比较块编号并重发ACK来处理这种情况。
  • 未处理服务器错误包： 如果文件不存在或磁盘满，服务器会回复ERROR包。客户端应该解析此包（操作码为5），并打印错误信息，而不是无限等待。

工程实践：超时、重传与状态机

以太网是不稳定的传输媒介。在实际项目中，我遇到过因为交换机瞬间拥堵导致升级失败的情况。一个健壮的Bootloader必须能处理网络超时和丢包。

场景：ACK包丢失

  • 现象： 进度卡在某个百分比不动。
  • 原因： 客户端发出的ACK包丢失，服务器在等待。
  • 解决： 服务器侧有超时重传机制（通常约3-5秒），客户端只需正确响应重复包即可。

场景：DATA包丢失

  • 现象： 客户端长时间收不到包，最终超时。
  • 原因： 网络链路丢包。
  • 解决： 客户端需要实现一个接收超时定时器。如果超过预定时间（如10秒）未收到任何数据包，应中断升级并报告网络错误。

场景：IP地址冲突

  • 现象： 设备无法ping通，网络初始化失败。
  • 原因： Bootloader使用的静态IP与网络中其他设备冲突。
  • 解决： 为Bootloader设计一个简单的故障恢复机制，例如连续3次网络初始化失败后，自动切换到一个备用的、不常用的IP地址。

实现超时控制，你需要一个精准的定时器（如SysTick）。将TFTP客户端的核心逻辑包装成一个状态机是清晰的做法。

编者提示： 在调试网络Bootloader时，务必准备一个网络抓包工具，如Wireshark。过滤TFTP协议（UDP端口69），你可以清晰地看到每一个RRQ、DATA、ACK包的交互过程。当升级卡住时，抓包能立刻告诉你到底是客户端没发ACK，还是服务器没发DATA。这是定位网络协议问题最直接有效的方法，比盲目看代码日志快得多。

下面是一个简化的超时处理状态机思路：

typedef enum {
    TFTP_STATE_IDLE,
    TFTP_STATE_WAIT_FIRST_DATA, // 发送RRQ后等待第一个DATA包
    TFTP_STATE_WAIT_NEXT_DATA,   // 发送ACK后等待下一个DATA包
    TFTP_STATE_TIMEOUT,
    TFTP_STATE_ERROR,
    TFTP_STATE_DONE
} tftp_state_t;

void tftp_timeout_check(void) {
    static uint32_t last_packet_time = 0;
    uint32_t now = get_system_tick();

    if (current_state == TFTP_STATE_WAIT_FIRST_DATA ||
        current_state == TFTP_STATE_WAIT_NEXT_DATA) {
        if ((now - last_packet_time) > TFTP_TIMEOUT_MS) {
            current_state = TFTP_STATE_TIMEOUT;
            printf("TFTP timeout, aborting.\r\n");
            // 清理资源，重置状态
        }
    }
}
// 在收到任何有效DATA包时，更新 last_packet_time

Bootloader的网络配置与启动

Bootloader需要知道服务器的IP地址和固件文件名。有几种常见的配置方式：

  1. 硬编码： 最简单，但缺乏灵活性。
  2. 通过串口配置： 在进入网络升级模式前，通过串口命令行设置IP和文件名。
  3. DHCP动态获取： Bootloader支持DHCP客户端，自动获取IP。但需要注意，如果DHCP服务器不可用，必须有超时回退机制（如使用静态链路本地地址169.254.x.x）。
  4. 从Flash或EEPROM读取： 应用程序在运行期间将配置参数写入特定Flash区域，Bootloader启动后读取。

对于大多数工业应用，我推荐“静态IP + 可配置”的组合。Bootloader默认使用一个预定义的静态IP（如192.168.1.100），但同时提供一个简化的串口菜单，允许用户在升级前临时修改目标服务器IP。这样既保证了上电即可用的便利性，又提供了必要的灵活性。

动手试一试

1. 搭建TFTP服务器： 在你的电脑上安装一个TFTP服务器软件（如Tftpd64）。将其根目录设置为存放你的固件.bin文件的文件夹。

2. 修改串口Bootloader： 在你已有的串口IAP Bootloader工程中，使用STM32CubeMX添加ETH外设和LwIP协议栈，生成初始化代码。

3. 集成TFTP客户端： 参考本章的代码框架，实现一个最简单的TFTP客户端。暂时不处理超时和重传，只实现基本的RRQ-DATA-ACK循环。

4. 测试： 将设备与电脑用网线直连，设置设备IP与电脑在同一网段。在Bootloader中触发网络升级，观察TFTP服务器日志和设备输出，确认固件开始传输。

本章小结

  • 以太网升级的核心是为Bootloader集成轻量级LwIP协议栈，并基于UDP实现TFTP客户端协议。
  • TFTP协议简单可靠，通过DATA/ACK握手机制传输文件，客户端必须正确处理字节序、重复包和超时。
  • 工程实现的关键在于引入状态机和超时重传逻辑，以应对不稳定的网络环境，并使用抓包工具进行调试。
  • Bootloader的网络配置（IP、服务器地址）可采用静态默认值与临时配置相结合的方式，兼顾便利与灵活。
