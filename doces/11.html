核心概念中断向量表核心概念函数指针跳转

当Bootloader将新的应用程序固件写入Flash的指定区域后，最关键的一步就是让CPU离开Bootloader，去执行那个刚刚写入的新程序。这个过程不是简单的函数调用，而是一次彻底的“控制权交接”。如果交接不当，系统会立刻跑飞或陷入硬件错误。

生活类比： 想象一下接力赛跑。Bootloader是前一棒运动员，App是后一棒。跳转机制就是交接棒的过程。仅仅把棒（固件数据）放在地上（写入Flash）是不够的，前一棒必须停下来，明确地把控制权交给后一棒，并且后一棒必须站在正确的起跑线（中断向量表）上准备起跑。本章要解决的就是如何完成这次完美交接。

技术定义： 应用程序跳转机制是指，在Bootloader环境中，通过软件方法将CPU的程序计数器（PC）和栈指针（SP）重置到用户应用程序的入口地址，并关闭当前环境的中断，使系统从用户应用程序的起始位置开始执行的过程。

跳转前的核心准备：中断向量表

在深入跳转代码之前，必须理解一个核心概念：中断向量表（Vector Table）。对于Cortex-M内核的STM32，上电或复位后，CPU会从内存地址0x0000 0000处取出第一个值作为栈顶指针（MSP），从0x0000 0004处取出第二个值作为复位向量（程序入口地址）。这张表里还依次存放着所有中断服务函数的入口地址。

地址 0x0000 0000
→
主栈指针 (MSP)
↓
地址 0x0000 0004
→
复位向量 (Reset_Handler)
↓
后续地址
→
NMI, 硬错误等中断向量

默认情况下，Flash的起始地址（0x0800 0000）被映射到0x0000 0000。所以Bootloader的向量表就位于0x0800 0000。当我们要跳转到位于偏移地址（例如0x0800 8000）的App时，App必须有它自己的向量表，并且CPU需要知道这个新表的位置。

关键点：向量表偏移寄存器 (VTOR)

Cortex-M3/M4/M7等内核提供了向量表偏移寄存器（VTOR）。通过设置这个寄存器，可以告诉CPU中断向量表的新位置。这是实现Bootloader和App共存并正确响应中断的硬件基础。对于STM32F1等Cortex-M3内核，VTOR地址是0xE000ED08。

跳转操作的具体步骤

从Bootloader跳转到App不是一个单一操作，而是一系列严谨的步骤，目的是清理当前环境并为App创造一个干净的初始状态。

1. 关闭所有中断
→
2. 重置SysTick等内核定时器
→
3. 获取App的栈顶和入口地址
→
4. 设置MSP并跳转

下面我们通过一个典型的跳转函数实现来分解这些步骤。我在项目中曾因漏掉步骤2，导致App一运行SysTick中断就触发，而中断向量却还未正确指向App的处理函数，直接引发硬件错误。

/**
  * @brief  从Bootloader跳转到应用程序
  * @param  app_address: 应用程序的起始地址 (必须是0x200的倍数)
  * @retval 无
  */
void JumpToApplication(uint32_t app_address) {
    // 步骤1: 定义函数指针类型
    typedef void (*pFunction)(void);
    pFunction Jump_To_Application;

    // 步骤2: 检查目标地址是否有效（简单的栈指针值检查）
    uint32_t jump_address = *(__IO uint32_t*)(app_address + 4); // 复位向量地址
    if ((jump_address & 0x2FFE0000) != 0x20000000) {
        // 地址看起来不像指向SRAM（合法的程序入口），跳转失败处理
        Error_Handler();
        return;
    }

    // 步骤3: 关闭全局中断，防止在跳转过程中被中断打断
    __disable_irq();

    // 步骤4: 重置SysTick定时器（关键！）
    SysTick->CTRL = 0;
    SysTick->LOAD = 0;
    SysTick->VAL = 0;

    // 步骤5: 设置向量表偏移地址（如果内核支持VTOR）
    // SCB->VTOR = app_address & 0xFFFFFF80; // 对于支持VTOR的型号

    // 步骤6: 设置主栈指针(MSP)为应用程序的栈顶
    __set_MSP(*(__IO uint32_t*)app_address);

    // 步骤7: 获取应用程序的复位处理函数地址
    Jump_To_Application = (pFunction)*(__IO uint32_t*)(app_address + 4);

    // 步骤8: 执行跳转
    Jump_To_Application();
}

常见误区

  • 忘记关闭中断： 跳转前必须禁用全局中断。如果跳转中途发生中断，CPU会去Bootloader的向量表找中断处理函数，而此时Bootloader的上下文已被破坏，必然导致崩溃。
  • 忽略SysTick： 如果Bootloader使用了HAL_Delay()或基于SysTick的延时，SysTick中断是开启的。跳转前必须彻底关闭它，否则它会在App中继续触发，但中断向量可能还未指向App的SysTick_Handler。
  • 地址不对齐： Cortex-M内核要求向量表地址必须至少128字节对齐（具体对齐要求请查阅芯片参考手册）。传递给跳转函数的app_address必须满足这个对齐要求。

应用程序（App）侧的必备配置

跳转是双向的配合。Bootloader做好了“推”的动作，应用程序也必须做好“接”的准备。App项目的配置错误是导致跳转后黑屏或无反应的常见原因。

应用程序关键配置项
配置项作用典型设置（以App起始地址0x08008000为例）
IROM1起始地址告诉链接器程序从Flash的哪个位置开始存放0x08008000
中断向量表偏移通过宏定义或代码设置VTOR，使中断能正确响应在main()开头调用 `SCB->VTOR = 0x08008000;`
链接脚本修改确保代码和数据被链接到正确的地址范围修改`.ld`(GCC)或`.sct`(Keil/AC6)文件中的ROM区域定义

对于使用STM32CubeIDE或Keil的开发者，修改IROM1起始地址是最关键的一步。这个地址必须与Bootloader中执行跳转时传入的`app_address`完全一致。

编者提示： 一个非常隐蔽的坑是关于中断优先级的。如果Bootloader中修改过中断优先级分组（例如调用了`HAL_NVIC_SetPriorityGrouping`），跳转到App后，这个分组设置依然有效。如果App的中断优先级配置基于不同的分组假设，可能会导致中断嵌套行为异常。稳妥的做法是，在App的`main`函数初始化阶段，重新配置一次中断优先级分组，确保配置符合预期。

启动文件与链接脚本的调整

除了IDE配置，我们还需要关注底层文件：启动文件和链接脚本。它们决定了代码的物理存放位置。

STM32CubeIDE (GCC)

  • 启动文件： 通常无需修改，向量表地址由链接脚本决定。
  • 链接脚本(.ld)： 修改`MEMORY`区域的`ROM`定义，将`ORIGIN`改为应用程序起始地址（如0x08008000）。

Keil MDK (ARMCC/AC6)

  • 启动文件： 无需修改。
  • 分散加载文件(.sct)： 在Options for Target -> Linker中取消勾选“Use Memory Layout from Target Dialog”，然后编辑`.sct`文件，修改`LR_IROM1`的起始地址。

IAR EWARM

  • 启动文件： 无需修改。
  • 链接配置文件(.icf)： 修改`define symbol __ICFEDIT_region_ROM_start__`的值为应用程序起始地址。

实际开发中，大部分团队会为App项目创建独立的链接脚本副本，与Bootloader项目的配置区分开，避免混淆。

跳转机制的延伸：软复位与参数传递

基础的跳转实现了功能，但一个健壮的IAP系统还需要考虑更多。

软复位跳转

有时我们希望在Bootloader完成升级后，不是直接跳转，而是执行一次软复位，让芯片从0x0800 0000重新启动，依靠Bootloader的启动逻辑再次判断并跳转到App。这种做法更“干净”，能完全初始化所有外设。实现方法是设置一个标志位在备份寄存器或特定Flash地址，然后调用`NVIC_SystemReset()`。

参数传递： Bootloader可能需要传递一些信息给App，例如固件版本、升级状态或校验和。这可以通过在固定的内存地址（例如App向量表之前的保留区域）写入数据来实现。App启动后，可以从这个约定好的地址读取数据。

// Bootloader端：写入参数到约定地址 (例如 App地址 - 0x200)
#define APP_PARAM_ADDRESS (APP_START_ADDRESS - 0x200)
typedef struct {
    uint32_t firmware_version;
    uint8_t  update_status;
} AppParam_t;

AppParam_t param = {0x01020003, 0x01}; // 版本1.2.3，状态正常
HAL_FLASH_Program(FLASH_TYPEPROGRAM_WORD, APP_PARAM_ADDRESS, (uint32_t)&param);
// 注意：实际编程需要按字对齐并解锁Flash，此处为示意

调试技巧： 当跳转失败，App没有运行时，首先检查Bootloader跳转函数传入的地址是否正确。然后，使用调试器连接到芯片，直接查看目标地址（APP_START_ADDRESS）和APP_START_ADDRESS+4的内容。前者应该是一个合理的SRAM地址（栈顶），后者应该指向App的Reset_Handler函数地址。如果这两个值看起来是0xFFFFFFFF或0x00000000，说明固件没有正确写入或地址配置错误。

  3. 先通过调试器将App程序直接下载到0x08008000起始的Flash区域。
  4. 运行Bootloader，并调用跳转函数，观察是否能成功跳转并运行App（LED闪烁）。
  5. 尝试在跳转函数中注释掉关闭SysTick的步骤，观察现象是否发生变化。

本章小结

  • 应用程序跳转的本质是将CPU的PC和SP寄存器重置到用户应用程序的入口，并清理Bootloader的运行环境。
  • 中断向量表重映射（通过VTOR）是确保App能正确响应中断的关键，跳转前必须关闭所有已开启的中断（尤其是SysTick）。
  • 成功的跳转需要Bootloader和App两侧配合：Bootloader正确执行跳转序列，App项目配置正确的起始地址并在代码中重映射向量表。
  • 通过检查目标地址的栈顶值和复位向量值，可以在跳转前进行有效性验证，提高系统鲁棒性。
  • 参数传递和软复位是构建更复杂、更可靠IAP系统的可选进阶技术。
