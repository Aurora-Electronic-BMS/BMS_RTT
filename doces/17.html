核心概念固件加密安全传输

当你的设备通过网络或串口暴露在外部时，裸奔的固件升级通道就像家门没锁。我在一个车载项目里就遇到过，竞品公司轻易地通过CAN总线抓取了我们的固件包进行反向分析。从这一章开始，我们为Bootloader装上“防盗门”和“监控摄像头”。

生活类比

快递包裹：你收到的快递，外面有胶带密封（完整性校验），里面可能还有带密码的盒子（加密），只有你知道密码（密钥）才能打开。固件安全传输也是如此，既要保证数据在传输途中没被调包（完整性），也要防止别人偷看内容（机密性）。

17.1 为何需要安全传输？

一个不安全的Bootloader会带来三大风险：知识产权泄露、系统被恶意控制和设备变砖。攻击者可以窃取你的算法，上传带有后门的固件，或者发送错误数据导致Flash写入失败。

关键点：安全目标

  • 机密性：固件内容对未授权者不可读。解决“偷看”问题。
  • 完整性：确保接收到的固件数据未被篡改。解决“调包”问题。
  • 身份验证：确认升级指令来自合法的上位机。解决“冒充”问题。

17.2 安全升级的核心组件

实现上述目标，我们需要三个技术组件协同工作：加密算法、哈希算法和密钥管理。它们在安全升级流程中各司其职。

对于大多数STM32的IAP应用，AES-128/256加密配合SHA-256校验是性价比最高的组合。硬件支持AES和SHA的型号（如STM32F4、F7、H7）应优先启用硬件加速，性能可提升数十倍。

常见误区

  • 混淆加密与校验：CRC或简单的累加和只能检测偶然错误，无法抵御恶意篡改。完整性校验必须使用密码学哈希（如SHA-256）。
  • 密钥硬编码在代码中：将密钥以明文形式写在代码里，等于把钥匙挂在门上。攻击者通过反编译即可提取。
  • 只加密不校验：加密可以防止偷看，但如果攻击者截获密文并替换，设备解密后得到的是乱码，可能导致系统崩溃。必须加密和校验同时进行。

17.3 集成加密与哈希库

STM32CubeMX和HAL库为我们提供了集成安全算法的便捷路径。如果你的芯片有硬件加密外设，强烈建议使用它。

以下是在Bootloader中初始化硬件AES并加密一个数据块的示例。这里使用AES-128 ECB模式，这是最简单的一种模式。实际项目中，为了更安全，你可能会选择CBC或CTR模式。

// 1. 外设句柄与密钥定义
CRYP_HandleTypeDef hcryp;
uint8_t aes_key[16] = {0x00, 0x01, 0x02, 0x03, 0x04, 0x05, 0x06, 0x07,
                     0x08, 0x09, 0x0A, 0x0B, 0x0C, 0x0D, 0x0E, 0x0F}; // 示例密钥，切勿直接使用！
uint8_t plaintext[16]; // 待加密的明文块（16字节）
uint8_t ciphertext[16]; // 加密后的密文块

// 2. 初始化AES硬件
void AES_Init(void) {
    hcryp.Instance = CRYP;
    hcryp.Init.DataType = CRYP_DATATYPE_8B;
    hcryp.Init.KeySize = CRYP_KEYSIZE_128B;
    hcryp.Init.pKey = aes_key;
    // 更多模式配置...具体需参考Cube HAL手册
    if (HAL_CRYP_Init(&hcryp) != HAL_OK) {
        // 初始化错误处理
    }
}

// 3. 加密一个数据块
int Encrypt_Block(uint8_t *in, uint8_t *out) {
    if (HAL_CRYP_AESECB_Encrypt(&hcryp, in, 16, out, 10) != HAL_OK) { // 超时10ms
        return -1; // 加密失败
    }
    return 0;
}

编者提示：密钥存储的坑
上面代码中密钥是硬编码的，这非常不安全。在实际项目中，密钥应该存储在芯片的只读保护区域（如STM32的RDP等级1/2下的Flash）或专用安全存储区（如STM32H5的TrustZone安全存储，或STM32L5的OTP区域）。对于没有这些功能的型号，一个折中方案是在生产时通过安全渠道（如调试接口）将唯一密钥注入到芯片的Flash固定地址，并在Bootloader启动后读取到RAM中使用，同时将主Flash设为读保护。

17.4 设计安全升级协议

有了加密和校验工具，我们需要重新设计上位机与Bootloader之间的通信协议。一个安全协议帧至少应包含密文数据、完整性校验码（哈希值），有时还需要随机数（Nonce）来防止重放攻击。

基础安全帧

  • 帧头：标识帧开始
  • 序列号/随机数：防重放
  • 密文数据：加密后的固件块
  • 消息验证码(MAC)：基于密钥的哈希值
  • 帧尾：校验和

握手与密钥协商

  • Bootloader上电后生成随机挑战码
  • 上位机用预共享密钥加密挑战码并返回
  • Bootloader验证通过后，才进入升级模式
  • 可基于会话生成临时密钥

这里有个隐藏的坑：哈希值必须在加密后计算。正确的流程是“加密->生成哈希(MAC)”，而不是“生成哈希->加密”。如果先哈希再加密，攻击者虽然不能篡改明文，但可以替换整个“密文+加密后的哈希”包。而先加密再对密文生成MAC，则可以确保整个数据包的完整性。

17.5 Bootloader侧的安全处理流程

在Bootloader中，收到安全帧后的处理逻辑比普通帧复杂。每一步验证失败都必须立即终止并返回错误，绝不能继续执行。

// 安全升级数据包处理伪代码
int Handle_Secure_Firmware_Packet(uint8_t *packet, uint32_t len) {
    uint8_t cipher_block[16];
    uint8_t received_mac[32]; // SHA-256输出32字节
    uint8_t computed_mac[32];

    // 1. 解析包，提取密文和接收到的MAC
    parse_packet(packet, cipher_block, received_mac);

    // 2. 验证序列号/随机数，防止重放攻击（此处简化）
    if (is_replay_attack()) return ERROR_REPLAY;

    // 3. 计算收到密文的MAC
    HAL_HASH_SHA256_Start(&hhash, cipher_block, 16, computed_mac, 100);

    // 4. 比对MAC，验证完整性
    if (memcmp(received_mac, computed_mac, 32) != 0) {
        return ERROR_INTEGRITY_FAIL; // 完整性校验失败，数据可能被篡改
    }

    // 5. MAC验证通过，解密数据
    uint8_t plain_block[16];
    if (HAL_CRYP_AESECB_Decrypt(&hcryp, cipher_block, 16, plain_block, 10) != HAL_OK) {
        return ERROR_DECRYPT_FAIL;
    }

    // 6. 将解密后的明文数据写入Flash缓存
    Write_To_Flash_Buffer(plain_block);
    return SUCCESS;
}

如果你看到解密后的数据全是乱码，但MAC校验却通过了，大概率是加密和解密使用的密钥不一致，或者加密/解密模式（如ECB、CBC）不匹配。务必确保上位机加密和Bootloader解密的参数完全相同。

动手试一试

在STM32CubeIDE中，为你的Bootloader项目添加安全功能：

  1. 使用STM32CubeMX为你的目标芯片（如STM32F407）使能CRYP和HASH外设（如果支持）。
  2. 生成代码，在Bootloader初始化函数中调用HAL_CRYP_Init和HAL_HASH_Init。
  3. 编写一个测试函数，定义一个16字节的数组（如`{1,2,3...16}`）作为明文，用AES-128 ECB模式加密，然后立即解密，最后比较解密结果是否与原始明文一致。
  4. 尝试修改密文中的一个字节，然后计算其SHA-256哈希，观察它与原始密文的哈希值是否完全不同。

这个练习能帮你验证加密/解密流程和哈希校验功能是否正常工作，这是构建安全传输的基础。

检验你的理解

  1. 判断题：使用CRC32校验码可以有效地防止黑客恶意篡改固件数据。（对/错）
  2. 选择题：在资源有限的STM32 Bootloader中，为实现固件传输的机密性和完整性，最常用的组合是：
    A) RSA加密 + MD5校验
    B) AES加密 + SHA-256校验
    C) XOR简单加密 + CRC校验
    D) 不加密，只使用累加和校验
  3. 判断题：安全的做法是先对固件数据计算哈希值，然后再进行加密传输。（对/错）

本章小结

  • 安全升级的核心目标是保障固件的机密性、完整性和升级源的身份验证。
  • 在嵌入式场景下，AES对称加密配合SHA-256哈希算法是实用且高效的安全组合，应优先利用STM32的硬件加密外设。
  • 密钥必须安全存储，避免硬编码，可考虑利用芯片的读保护、OTP或安全存储区。
  • 设计安全协议时，应采用“先加密，后对密文生成消息验证码(MAC)”的顺序，并加入序列号等机制防止重放攻击。
  • Bootloader处理安全数据包时，必须严格执行“验证->解密->写入”的流程，任何一步失败都必须中止升级。
