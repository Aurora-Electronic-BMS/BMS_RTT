核心概念FATFSSDMMC

当设备部署在偏远现场或需要同时升级大批量设备时，通过串口或网络逐台连接升级变得低效。SD卡升级方案应运而生，它允许你将固件文件（如`firmware.bin`）拷贝到SD卡，设备上电后自动检测并完成升级，整个过程无需连接电脑。

生活类比： 就像你把新的导航地图数据包（固件文件）下载到U盘里，然后插到车载导航仪上，导航仪会自动识别并更新地图。SD卡升级的核心就是让STM32 Bootloader扮演这个“导航仪”，能自动读取存储卡里的“数据包”。

技术定义： SD卡升级是指Bootloader通过SDMMC（Secure Digital MultiMediaCard）或SPI接口访问SD卡存储介质，并借助文件系统（通常是FATFS）定位、读取固件文件，最终将其写入内部Flash的应用程序区域的过程。

上图清晰地展示了数据流向。整个流程始于用户将固件文件放入SD卡，Bootloader启动后，依次通过文件系统层、存储驱动层和硬件接口访问SD卡，读取文件内容。这里涉及两个关键技术栈：硬件接口（SDMMC或SPI）和软件中间件（FATFS文件系统）。

接口选择：SDMMC vs SPI

STM32通常提供两种方式访问SD卡：

  • SDMMC接口： 这是专用高速接口，使用4位数据线（SDMMC_D[3:0]）和时钟线（SDMMC_CK），性能高，是首选方案。大部分STM32F4/F7/H7系列都支持。
  • SPI接口： 使用标准的SPI总线（MOSI, MISO, SCK）和一根片选线（CS），兼容性好，但速度较慢。通常在芯片没有SDMMC外设或引脚紧张时使用。

我在一个使用STM32F407的项目中，因为PCB布线原因SDMMC信号质量不佳，不得不切换到SPI模式，升级一个1MB的固件耗时从约2秒增加到近10秒。对于Bootloader，速度不是首要考虑，可靠性更重要，两种方式都可以。

使用STM32CubeMX集成FATFS与SD卡驱动

最快捷的方式是使用STM32CubeMX进行图形化配置，它能自动生成SD卡硬件初始化和FATFS中间件代码，大幅减少底层开发工作量。

配置完成后生成代码，你的工程将自动包含`fatfs.c/.h`、`sd_diskio.c`（SDMMC模式）或`spi_diskio.c`（SPI模式）。Bootloader的`main`函数中，在初始化完硬件后，需要调用`MX_FATFS_Init()`来初始化文件系统。

常见误区

  • SD卡未格式化或格式不对： Bootloader通常只支持FAT32（或exFAT，如果使能）。使用Windows的“格式化”工具，选择FAT32格式，分配单元大小选默认（通常是4096字节）或16KB。
  • 硬件初始化顺序错误： 必须先初始化SDMMC/SPI硬件，再初始化FATFS。顺序反了会导致`f_mount`失败。
  • 忽略SD卡检测引脚： 很多SD卡座自带卡检测（CD）引脚。如果硬件有此设计，必须配置该GPIO为输入模式并上拉，在代码中读取其状态来判断卡是否插入，避免对空卡座进行操作导致死机。

Bootloader读取固件文件的核心流程

初始化成功后，Bootloader需要执行一个固定的流程来查找并读取固件文件。这个流程比串口接收更结构化，因为它是在文件系统上操作。

上电进入Bootloader
→
初始化SD卡与FATFS
→
挂载SD卡根目录
→
查找特定固件文件
打开文件并获取大小
→
分块读取、校验并写入Flash
→
关闭文件，跳转应用

下面是一个简化的代码框架，展示了如何使用FATFS API完成上述流程的关键步骤：

// 包含FATFS头文件
#include "fatfs.h"
// 定义固件文件名，可放在根目录或特定文件夹
#define FIRMWARE_FILE_NAME  "/firmware.bin"
// FATFS工作区与文件对象
FATFS fs;
FIL file;
UINT bytes_read;

int SD_Card_Upgrade(void) {
    FRESULT res;
    // 1. 挂载文件系统，“0:”代表第一个驱动器（SD卡）
    res = f_mount(&fs, "0:", 1);
    if (res != FR_OK) {
        // 挂载失败，可能是卡未插入或格式不对
        return -1;
    }

    // 2. 打开固件文件
    res = f_open(&file, FIRMWARE_FILE_NAME, FA_READ);
    if (res != FR_OK) {
        f_unmount("0:");
        return -2; // 文件不存在
    }

    // 3. 获取文件大小，用于校验和进度显示
    FSIZE_t file_size = f_size(&file);
    // 此处可添加：检查文件大小是否超过应用程序区容量

    // 4. 分块读取文件并写入Flash（假设已有Write_Flash函数）
    uint8_t buffer[512]; // 读取缓冲区
    uint32_t app_address = APPLICATION_ADDRESS; // 应用起始地址
    while (1) {
        res = f_read(&file, buffer, sizeof(buffer), &bytes_read);
        if (res != FR_OK || bytes_read == 0) {
            break; // 读取完毕或出错
        }
        // 将buffer中的数据写入Flash的app_address处
        if (Write_Flash(app_address, buffer, bytes_read) != 0) {
            f_close(&file);
            f_unmount("0:");
            return -3; // Flash写入失败
        }
        app_address += bytes_read;
        // 此处可添加：喂看门狗、更新进度等
    }

    // 5. 收尾工作
    f_close(&file);
    f_unmount("0:");
    // 6. 校验固件完整性（如CRC32），然后跳转
    if (Verify_Firmware() == 0) {
        Jump_To_Application();
    }
    return -4; // 校验失败
}

编者提示：文件路径与长文件名
实际项目中，固件文件可能不在根目录，而是放在`/upgrade/firmware_v1.2.3.bin`这样的深层路径中。FATFS默认可能不支持长文件名和深层目录。你必须在`ffconf.h`（由CubeMX生成）中启用`_USE_LFN`（设置为1或2）和`_FS_RPATH`（设置为1或2）。启用`_USE_LFN`会消耗更多RAM（用于文件名缓冲区），在Bootloader中需要仔细评估内存使用。

增强可靠性：升级状态与错误处理

一个健壮的SD卡升级Bootloader不能只是“读文件-写Flash”，还需要考虑各种异常情况并给用户明确的反馈。

场景：升级中断

  • 问题： 升级中途断电，Flash中是不完整的固件。
  • 方案： 在Flash中开辟一个“升级状态标志区”。升级开始前写`UPGRADE_START`，成功完成后写`UPGRADE_OK`。Bootloader启动时检查标志，若为`START`则说明上次升级失败，应停留在Bootloader或尝试恢复。

场景：多固件文件

  • 问题： 卡里有多个`.bin`文件，该升级哪一个？
  • 方案： 定义明确的命名规则，如使用版本号`fw_v1.2.3.bin`。Bootloader可以读取一个额外的配置文件`upgrade.cfg`，里面指定本次要升级的文件名。

场景：用户反馈

  • 问题： 用户插入卡后，设备毫无反应。
  • 方案： 利用板载LED或蜂鸣器提供状态指示。例如：LED慢闪（寻找文件中）→ 快闪（升级中）→ 常亮（升级成功）→ 特定错误码闪烁（如文件未找到、校验失败）。

对于状态标志，一个简单的实现如下：

typedef enum {
    APP_VALID = 0x5A5A5A5A,
    UPGRADE_REQUEST = 0xA5A5A5A5,
    UPGRADE_IN_PROGRESS = 0xCCCCCCCC,
} Upgrade_Flag_t;

// 在Flash的固定位置（如Bootloader尾部）定义标志变量
#define UPGRADE_FLAG_ADDRESS   (0x0800F000) // 示例地址，需根据实际内存映射调整
volatile Upgrade_Flag_t *const pUpgradeFlag = (Upgrade_Flag_t*)UPGRADE_FLAG_ADDRESS;

// Bootloader开始时检查
if (*pUpgradeFlag == UPGRADE_IN_PROGRESS) {
    // 上次升级未完成，进入错误处理流程（如尝试再次升级或报错）
    Handle_Failed_Upgrade();
}

性能与内存优化
Bootloader对空间极其敏感。使用CubeMX生成代码时，选择LL库并关闭不必要的FATFS功能（如编码转换`_CODE_PAGE`、`_USE_FIND`等）。读取缓冲区（示例中的`buffer[512]`）大小需要权衡：太大会占用宝贵RAM（尤其是SRAM小的型号如STM32F103），太小会增加Flash写入次数（因为Flash编程通常以页为单位，如2KB）。建议缓冲区大小设为Flash编程页大小的整数倍。

本章小结

  • SD卡升级是一种离线、大容量的固件更新方案，核心是集成FATFS文件系统来访问SD卡上的固件文件。
  • 硬件上可选择SDMMC（高速）或SPI（通用）接口与SD卡通信，使用STM32CubeMX可以快速完成底层驱动和FATFS中间件的配置与代码生成。
  • 升级流程包括：挂载文件系统→打开固件文件→分块读取→写入Flash→校验→跳转。必须处理好文件查找、路径、长文件名等细节。
  • 工业级实现需要考虑升级状态标志、用户反馈（LED/蜂鸣器）和异常处理（如断电恢复），以增强可靠性。
  • Bootloader代码空间紧张，务必通过选择LL库、裁剪FATFS功能、合理设置缓冲区大小来进行优化。
