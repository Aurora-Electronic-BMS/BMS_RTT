核心概念共享内存命令协议

当Bootloader成功跳转到应用程序后，两者并非“老死不相往来”。在实际项目中，应用程序可能需要主动请求升级，或者向Bootloader报告自身状态。这就需要一种在两者之间传递信息的机制。

共享内存：Bootloader与App的“留言板”

想象一下合租的室友，你们有一个公用的冰箱贴留言板。Bootloader和App就像两个室友，共享内存区域就是那块留言板。任何一方都可以在上面留下信息，另一方在需要时去读取。这是一种简单、高效且不依赖实时通信外设的交互方式。

从技术上讲，共享内存是一块被Bootloader和App工程共同约定使用的、固定的SRAM或备份寄存器区域。双方通过读写这块内存中的特定数据结构来交换命令和状态。

共享内存区域的设计

设计共享内存，首要任务是确定地址和数据结构。地址必须落在Bootloader和App都能安全访问的RAM范围内，并且要避开双方的栈、堆等动态内存区域。

以STM32F407（192KB SRAM）为例，一个典型的内存划分如下表所示。我们将共享区放在RAM末尾，这样对双方的内存布局影响最小。

区域起始地址大小说明
Bootloader使用区0x2000 0000约 20KBBootloader的栈、堆、全局变量
应用程序使用区0x2000 5000约 160KBApp的栈、堆、全局变量（需在IDE中配置）
共享内存区0x2002 F0001KBBootloader与App的通信区域

确定了地址，接下来设计数据结构。这个结构体需要包含通信所需的全部信息，并且要考虑字节对齐和可能的校验。

// boot_app_shared.h - Bootloader与App共用的头文件
#pragma once
#include <stdint.h>

#define SHARED_MEMORY_BASE  (volatile void*)0x2002F000

typedef enum {
    CMD_NOP = 0x00,          // 无操作
    CMD_REQUEST_JUMP_TO_BL = 0x55, // App请求跳回Bootloader
    CMD_FIRMWARE_VALID = 0xAA,     // App确认自身固件有效
    CMD_REPORT_STATUS = 0xCC,      // App上报运行状态
} BootloaderCommand_t;

typedef struct __attribute__((packed)) {
    uint32_t magic;          // 魔数，用于标识结构已初始化，如 0xDEADBEEF
    BootloaderCommand_t command; // 当前待执行的命令
    uint32_t app_version;    // App存储的自身版本号
    uint32_t app_status;     // App自定义状态字
    uint8_t  reserved[16];   // 保留字段，为未来扩展预留
    uint32_t crc32;          // 整个结构体的CRC校验值（不含crc32字段自身）
} SharedMemory_t;

关键设计要点

  • 使用volatile指针：共享内存的指针必须用volatile修饰，防止编译器优化掉看似“无意义”的读写操作。
  • 包含魔数(Magic Number)：用于判断共享内存是否已被初始化。Bootloader启动时应检查此值，若无效则进行初始化。
  • 结构体紧凑打包：使用__attribute__((packed))（GCC/ARMCC）或#pragma pack(1)（IAR）确保结构体无填充字节，保证在不同编译环境下布局一致。
  • 加入CRC校验：防止内存位翻转或意外篡改导致读取到错误数据。这是提升通信可靠性的关键一步。

双向通信流程与实现

共享内存准备好后，Bootloader和App就可以按约定的协议进行通信了。通信是双向的，但通常由App发起请求，Bootloader在下次启动时响应。

“跳回Bootloader”的请求。我在一个车载控制器项目中就用过这个机制，当App通过CAN总线收到服务器下发的升级指令后，就会触发这个流程。

// app_main.c - 应用程序中的代码片段
#include "boot_app_shared.h"

void RequestJumpToBootloader(void) {
    SharedMemory_t* shared = (SharedMemory_t*)SHARED_MEMORY_BASE;
    
    // 1. 准备命令数据
    shared->command = CMD_REQUEST_JUMP_TO_BL;
    shared->app_version = 0x01020300; // 示例版本号：V1.2.3
    shared->app_status = 0; // 可以填入错误码或状态
    
    // 2. 计算并填充CRC（此处省略CRC计算函数细节）
    shared->crc32 = CalculateCRC32((uint8_t*)shared, sizeof(SharedMemory_t) - sizeof(uint32_t));
    
    // 3. 执行软复位，将控制权交还给Bootloader
    NVIC_SystemReset();
    // 代码执行不到这里
}

Bootloader端在启动初始化阶段，需要检查并处理共享内存中的命令。注意，Bootloader在跳转到App之前，应该将共享内存中的命令清零，避免下次启动时误触发。

// bootloader_main.c - Bootloader中的处理逻辑
#include "boot_app_shared.h"

void ProcessSharedMemoryCommand(void) {
    SharedMemory_t* shared = (SharedMemory_t*)SHARED_MEMORY_BASE;
    
    // 1. 检查魔数，判断共享内存是否已初始化
    if (shared->magic != 0xDEADBEEF) {
        InitSharedMemory(shared); // 初始化所有字段为0，并设置magic
        return;
    }
    
    // 2. 验证CRC，确保数据完整
    uint32_t saved_crc = shared->crc32;
    shared->crc32 = 0; // 计算CRC时需临时清零该字段
    uint32_t calc_crc = CalculateCRC32((uint8_t*)shared, sizeof(SharedMemory_t));
    shared->crc32 = saved_crc; // 恢复原值
    
    if (calc_crc != saved_crc) {
        // CRC校验失败，数据可能损坏，按无命令处理
        shared->command = CMD_NOP;
        return;
    }
    
    // 3. 根据命令执行相应操作
    switch (shared->command) {
        case CMD_REQUEST_JUMP_TO_BL:
            printf("App requested to stay in bootloader.\r\n");
            // 不执行跳转，停留在Bootloader等待升级指令
            EnterUpgradeMode();
            break;
            
        case CMD_FIRMWARE_VALID:
            // App自检成功，可以更新一些标志，比如记录“App运行正常”
            MarkAppAsValid(shared->app_version);
            break;
            
        case CMD_REPORT_STATUS:
            // 处理App上报的状态，可用于诊断
            HandleAppStatusReport(shared->app_status);
            break;
            
        case CMD_NOP:
        default:
            // 无命令或未知命令，正常执行跳转
            break;
    }
    
    // 4. 命令处理完毕，清除命令字段，防止重复触发
    shared->command = CMD_NOP;
    // 注意：这里需要重新计算并更新CRC32，因为command字段变了
    shared->crc32 = 0;
    shared->crc32 = CalculateCRC32((uint8_t*)shared, sizeof(SharedMemory_t) - sizeof(uint32_t));
}

常见误区

  • 忘记CRC校验：直接信任内存中的数据非常危险。SRAM可能因电源毛刺发生位翻转，导致读取到错误的命令。CRC校验是工业级设计的基本要求。
  • Bootloader不清除命令：如果Bootloader处理完命令后不将其重置为CMD_NOP，那么下次MCU复位（非App触发）时，Bootloader会再次执行同一个命令，可能导致意外行为。
  • 地址未在链接脚本中排除：App工程的链接脚本必须将共享内存区域排除在零初始化（.bss）和初始化（.data）段之外，否则启动时可能会覆盖掉已设置好的命令数据。

编者提示：关于共享内存的“初始化”时机
一个容易被忽略的细节是共享内存的初始化。你不能假设芯片上电后SRAM是全零的。实际上，SRAM的内容是随机的。因此，Bootloader在第一次访问共享内存时，必须通过“魔数”判断其是否已被初始化。如果魔数不对，Bootloader需要将整个结构体清零并写入正确的魔数。这个初始化动作只在共享内存从未被使用过时执行一次，之后魔数会一直保持有效。

高级应用：状态上报与诊断

共享通信机制不仅用于请求升级，还可以成为简单的诊断通道。例如，App可以在每次启动时向Bootloader报告“我成功启动了”，或者上报一些运行时的错误码。

上电自检报告

  • App启动后进行自检
  • 将结果写入共享内存
  • 复位后Bootloader读取结果并决定动作（如：自检失败则停留在Bootloader）

运行时错误记录

  • App发生严重错误时，将错误码写入共享内存
  • 执行软复位
  • Bootloader读取错误码，并通过串口/USB上报给上位机

双备份切换协调

  • App判断需要切换到备份固件
  • 通过共享内存告知Bootloader目标固件位置
  • Bootloader执行跳转或激活备份

实现状态上报时，可以在SharedMemory_t结构体中增加更多字段，比如错误码数组、时间戳、或者特定的标志位。实际开发中，大部分团队会预留足够的保留字段（reserved[16]）以备未来扩展，而不是每次升级通信协议都修改结构体定义。

动手试一试

在你的STM32CubeIDE中创建两个工程：一个Bootloader，一个App。按照本章的指引，完成以下任务：

  1. 在Bootloader工程中定义boot_app_shared.h文件，包含SharedMemory_t结构体定义，并约定共享内存地址为0x2002F000。
  2. 修改Bootloader的启动代码，在跳转到App前调用ProcessSharedMemoryCommand()函数。
  3. 在App工程中包含同一个头文件，并添加一个函数，当按下某个按键（如PA0）时，设置命令为CMD_REQUEST_JUMP_TO_BL，然后执行软复位。
  4. 编译下载后，先启动Bootloader，然后跳转到App。在App中按下按键，观察系统是否复位并停留在Bootloader（可以通过串口打印信息判断）。

提示：确保App工程的链接脚本（.ld文件）中，RAM的起始地址和长度避开了共享内存区域。例如，如果RAM总共192KB，共享区在最后1KB，那么App可用的RAM长度应配置为191KB。

检验你的理解

  1. 判断题：Bootloader与App通过共享内存通信时，必须使用volatile关键字来定义指向共享内存的指针，以防止编译器优化。（对/错）
  2. 选择题：Bootloader在启动时发现共享内存中的命令是“请求跳回”，它应该怎么做？
    • A. 立即跳转到应用程序
    • B. 清除该命令，然后跳转到应用程序
    • C. 停留在Bootloader模式，等待可能的升级操作
    • D. 将命令改写成“无操作”，然后跳转到应用程序
  3. 判断题：共享内存结构体中的CRC校验值，是为了防止App或Bootloader的程序代码被篡改。（对/错）

本章小结

  • 共享内存是Bootloader与App之间一种简单、高效的静态通信方式，如同一个共用的“留言板”。
  • 设计共享内存需要精确定义其物理地址和数据结构，结构体应包含魔数、命令、数据和CRC校验，并使用紧凑打包以避免对齐问题。
  • 通信流程通常由App发起（如设置升级请求命令后复位），Bootloader在下次启动时读取并响应命令，处理完毕后必须清除命令字段。
  • CRC校验是确保数据完整性的关键，不可或缺。共享内存区域需要在App的链接脚本中排除，防止被初始化覆盖。
  • 此机制可扩展用于App状态上报、诊断信息传递和双备份系统协调等高级功能。
