核心概念A/B分区回滚

想象一下你的手机系统升级：下载新版本，安装，重启。如果新系统启动失败，手机会自动回退到上一个能正常工作的版本，避免你拿着一块“砖头”。STM32上的双备份与回滚机制，就是为嵌入式设备实现类似的“后悔药”。

双备份机制：在Flash中划分两个独立的区域（通常称为A区和B区），交替存储新旧两版应用程序。任何时候，只有一个区域被标记为“活动”分区，用于启动运行。

我在一个车载仪表项目里踩过坑：一次远程OTA后，新固件因某个传感器驱动不兼容导致系统频繁重启，设备直接“变砖”，只能派人到现场用串口烧录器修复。从那以后，所有需要远程升级的产品，我都强制要求加入双备份回滚。

双备份存储布局设计

实现双备份的第一步，是重新规划你的Flash内存地图。你需要为两个应用程序副本、一个Bootloader以及一个用于存储状态信息的小区域分配空间。

状态标志区至关重要，它通常只有几个字节到几十个字节，存储在Flash的固定位置（例如Bootloader之后的第一个扇区）。Bootloader和应用程序都需要读写这个区域，以协商当前哪个分区是有效的、可启动的。

标志名称大小（字节）描述典型值示例
active_slot1当前活动分区标识0xA5表示A区，0x5A表示B区
update_status1升级过程状态0x00:空闲，0x01:新固件写入中，0x02:新固件待验证
boot_counter2启动尝试计数器每次启动尝试加1，成功启动后清零
crc32_value4活动分区固件的CRC32校验值由Bootloader在固件激活时计算并存储

实际开发中，大部分团队会选择将状态标志存放在一个独立的、较小的Flash扇区，例如STM32F4的扇区0（16KB）。这样擦写状态标志时，不会影响Bootloader或应用程序分区。你需要根据具体芯片的Flash扇区大小来调整布局。

Bootloader的增强启动逻辑

引入了双备份后，Bootloader的启动决策逻辑变得复杂。它不再简单地跳转到固定地址，而是需要先检查状态标志，决定跳转到哪个分区，并在跳转前进行健康检查。

这里有个隐藏的坑：CRC校验。你必须在应用程序编译后，计算整个应用程序映像（从向量表开始到结束）的CRC值，并将这个值作为已知常量提供给Bootloader。Bootloader在运行时，会读取Flash中的应用程序数据，重新计算CRC并与存储的已知值比较。如果使用STM32CubeIDE，可以在链接脚本后处理步骤中添加生成CRC并填充到固定地址的工具。

关键点：启动失败检测

如何知道新启动的应用程序运行失败了？常见方法有：

  • 独立看门狗（IWDG）超时：应用程序必须在主循环中定期喂狗。如果新固件有致命bug导致卡死，看门狗复位后，Bootloader会发现boot_counter在连续增加。
  • 软件标志：应用程序在初始化完成后，向一个RAM中的特定位置（或备份寄存器）写入“健康”标志。Bootloader在启动前检查该标志，如果标志未设置，则认为上次启动未成功。

我在项目中更倾向于结合使用两者：用软件标志快速判断，用看门狗应对完全卡死的情况。

IAP升级流程的改造

标准的IAP流程是“下载-擦除-写入-跳转”。在双备份系统中，流程变为“下载-写入备用分区-标记待验证-重启”。新固件写入的是当前非活动的那个分区（备用分区），从而保证任何时候都有一个已知良好的固件可以回退。

⚠️ 常见误区

  • 在活动分区上直接升级：这是最危险的错误。一旦写入过程中断电或出错，两个分区都损坏，设备无法启动。必须始终坚持“写入备用分区”原则。
  • 忘记更新状态标志：固件数据写完后，必须将update_status设置为“待验证”，并将active_slot指向新分区。如果忘记设置，Bootloader会直接启动旧分区，升级看似“失败”。
  • CRC计算范围不一致：Bootloader计算的CRC范围（起始地址、长度）必须与编译时工具生成的CRC范围完全一致，否则校验永远无法通过。

一个健壮的升级流程伪代码如下：

// 在Bootloader的升级处理函数中
void HandleFirmwareUpdate(void) {
    uint8_t current_active = ReadActiveSlot();
    uint8_t target_slot = (current_active == SLOT_A) ? SLOT_B : SLOT_A;

    // 1. 擦除目标分区（备用分区）
    FlashErase(target_slot_base_addr, target_slot_size);

    // 2. 接收并写入固件数据到目标分区
    while (data_remaining) {
        ReceiveFirmwareData(buffer, chunk_size);
        FlashProgram(target_addr, buffer, chunk_size);
        target_addr += chunk_size;
    }

    // 3. 计算并验证写入数据的CRC（可选，但推荐）
    calculated_crc = CalculateCRC(target_slot_base_addr, firmware_size);
    if (calculated_crc != expected_crc_from_pc) {
        SendErrorToPC("CRC mismatch after write");
        return;
    }

    // 4. 更新状态标志：新分区待验证，启动计数器清零
    WriteStatusFlag(UPDATE_STATUS, STATUS_PENDING_VERIFY);
    WriteStatusFlag(ACTIVE_SLOT, target_slot);
    WriteStatusFlag(BOOT_COUNTER, 0);

    // 5. 重启系统，让增强的Bootloader逻辑接管
    NVIC_SystemReset();
}

编者提示：关于状态标志的存储，有一个实用技巧。不要只存储一份标志，而是存储两份或三份（称为“冗余存储”），并在读取时采用“投票制”。例如，存储三个active_slot值，读取时如果两个是0xA5，一个是0x5A，则判定0xA5有效。这可以防止因Flash单比特翻转（虽然概率极低）导致的状态标志错误，进一步提升可靠性。实现时只需多写入几次，成本很低，但收益很高。

应用程序的配合与回滚触发

双备份机制需要应用程序的配合。应用程序启动后，需要尽快清除“启动尝试计数器”，并向Bootloader报告“我运行正常”。

通常，在应用程序的main函数开头，初始化了基本系统（时钟、必要外设）后，就应立即调用一个与Bootloader约定的接口函数：

// 在应用程序的main函数开始处调用
void App_ReportSuccessfulBoot(void) {
    // 1. 清除Bootloader使用的启动计数器
    ClearBootCounterInStatusArea();

    // 2. 将update_status设置为“空闲”，确认本次启动有效
    if (GetUpdateStatus() == STATUS_PENDING_VERIFY) {
        WriteStatusFlag(UPDATE_STATUS, STATUS_IDLE);
    }

    // 3. （可选）在备份寄存器或RAM中设置“健康”标志
    RTC_WriteBackupRegister(BOOT_HEALTHY_REG, BOOT_HEALTHY_MAGIC);
}

如果应用程序在运行一段时间后（非启动阶段）检测到自身功能异常，也可以主动请求回滚。这通常通过一个软复位，并在复位前设置特定的回滚请求标志来实现。

场景：新固件启动后功能异常

  • 应用程序检测到关键传感器无响应。
  • 调用RequestRollback()函数。
  • 该函数将状态标志的active_slot改回旧分区，并设置一个“回滚请求”标志。
  • 执行软复位，Bootloader下次将启动旧固件。

场景：升级后连续启动失败

  • 新固件有致命Bug，无法通过初始化。
  • 看门狗复位触发，Bootloader的boot_counter累加。
  • 当计数器超过阈值（如3次），Bootloader判定新分区失效。
  • 自动切换active_slot到旧分区，并启动。

实际开发中，你需要仔细设计回滚的触发条件，避免误判。例如，不要因为一次偶然的通信超时就触发回滚。

动手试一试

在你的STM32开发板上模拟实现双备份启动流程。即使没有实际的第二个应用程序，也可以通过修改链接脚本和Bootloader代码来演练。

  1. 修改链接脚本：为你的应用程序定义两个加载地址（例如0x08010000和0x08030000），并编译生成两个相同但地址不同的hex文件。
  2. 增强你的Bootloader：在Bootloader中实现一个简单的状态标志区（可以用芯片内部Flash的最后一个扇区模拟）。实现读取active_slot并跳转到对应地址的逻辑。
  3. 模拟升级：通过串口命令，让Bootloader“切换”活动分区标志，然后复位。观察Bootloader是否会跳转到另一个地址（你可以让两个应用程序的LED闪烁模式不同来区分）。

这个练习不涉及实际的Flash写入，重点在于理解状态管理和决策逻辑。

本章小结

  • 双备份机制通过在Flash中维护两个应用程序副本（A区和B区），为固件升级提供了可靠的“回退”能力，是防止设备变砖的关键设计。
  • 核心在于一个由Bootloader和应用程序共同维护的“状态标志区”，它记录了活动分区、升级状态和启动健康信息，是系统决策的大脑。
  • 升级流程必须遵循“写入备用分区”原则，确保任何时候都有一个已知良好的固件可用。
  • 回滚可以通过应用程序主动请求触发，也可以由Bootloader在检测到连续启动失败后自动执行。
  • 结合CRC校验、看门狗和软件健康标志，可以构建一个多层次、高可靠的启动失败检测与恢复系统。
