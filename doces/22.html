核心概念空中下载断点续传

当你的设备部署在楼顶、野外或者海外，通过有线方式升级固件变得不切实际。无线OTA（Over-The-Air）升级就像手机的系统更新，通过网络将新固件“推送”到设备，实现远程维护和功能迭代。我在一个智慧农业项目中，就因为设备分散在几百亩农田里，不得不连夜开发OTA功能，深刻体会到它的必要性。

什么是空中下载？

想象一下手机App的自动更新：你点击“更新”后，新版本程序包通过网络下载到手机，然后自动安装替换旧版本。无线OTA升级与此类似，只是更新的对象是嵌入式设备的整个系统固件，过程更复杂，风险也更高。

技术定义：空中下载（OTA）是一种通过无线通信网络（如Wi-Fi、蜂窝网络）远程更新嵌入式设备固件的技术。它通常包含固件包的下载、校验、存储和最终的Bootloader引导更新等完整流程。

无线OTA升级系统架构

一个完整的无线OTA系统不是单片机能独立完成的，它涉及云端、通信链路和设备端三个部分的协同工作。设备端是核心，但必须放在整个系统中理解。

上图中，云端服务器负责存储固件、管理设备升级策略；无线通信模块（如ESP8266、SIM800C）是桥梁；STM32设备端则包含应用程序（负责下载和触发）和Bootloader（负责最终的写入和跳转）。实际开发中，大部分团队会选择在应用程序中实现下载和校验逻辑，然后通过标志位或特定命令重启进入Bootloader完成烧写。

无线通信方案选型

选择哪种无线技术，直接决定了OTA的速率、成本、功耗和部署复杂度。没有最好的，只有最适合你项目场景的。

方案典型模块速率功耗适用场景集成复杂度
Wi-FiESP8266, ESP32高 (Mbps级)中高室内、有稳定Wi-Fi覆盖、固件较大（>1MB）中（需处理TCP/IP协议栈）
4G Cat.1移远EC200S, 广和通L610中 (Mbps级)中移动或广域覆盖、对速率有一定要求高（需处理PPP/AT指令、SIM卡）
NB-IoT移远BC260Y, 中兴ME3616低 (Kbps级)极低远程仪表、低速数据上报、小包固件差分升级中高（网络附着流程复杂）
蓝牙NRF52832, DA14580中 (Mbps级)低近距离维护、手机直连升级低（点对点传输）

我在一个共享设备项目中使用了Wi-Fi方案，因为固件有2MB多，且部署在商场内有稳定网络。但如果你的设备装在信号不佳的地下室，4G可能是更可靠的选择。对于水表、气表这类几年换一次电池的设备，NB-IoT的低功耗优势无可替代。

关键点：差分升级

对于NB-IoT等低速网络，传输完整的几MB固件包可能耗时数小时且费用高昂。差分升级（也叫增量升级）是解决方案。它只传输新版本和旧版本之间的差异部分（差分包），大小可能只有完整包的10%-20%。设备端收到差分包后，需要结合本地旧固件，在内存中“合成”出新固件，再交给Bootloader写入。这会增加设备端算法的复杂度（常用bsdiff/xdelta算法），但极大节省了流量和升级时间。

设备端OTA软件架构

在STM32的应用程序中，你需要设计一个独立的OTA任务或模块来管理整个无线下载流程。它与Bootloader的边界必须清晰。

→

是
→

→

复位后，Bootloader启动，检查到升级标志位，便会从缓存区读取已验证的固件，写入到应用程序区，完成最终的更新。

编者提示：务必为固件下载设计一个独立的Flash缓存区，不要边下载边直接写入目标应用区。因为无线传输可能中断，写到一半的应用程序区会损坏导致设备“变砖”。缓存区可以放在内部Flash末尾或外部SPI Flash中。下载完成后，先校验整个缓存区的数据完整性，确认无误后再设置标志位。这个“下载-校验-确认”的三步流程是保证可靠性的关键。

核心流程：断点续传与状态上报

无线网络不稳定是常态。下载一个2MB的固件包，中间很可能断线几次。如果没有断点续传，每次重连都从头开始下载，用户体验极差且浪费资源。

实现断点续传，需要设备端在非易失性存储（如Flash的特定扇区）中记录当前已成功下载的数据长度。每次连接服务器下载时，通过HTTP Header中的“Range”字段（例如 `Range: bytes=1024-`）告诉服务器：“我从第1024字节开始下载，前面的我已经有了”。服务器需要支持这一特性。

同时，设备端应该定期向服务器上报升级状态，例如：0:空闲, 1:下载中, 2:下载完成, 3:校验失败, 4:升级成功。这样在云端的管理界面上，你就能清晰地看到每一台设备的升级进度和结果。我在实际项目中就通过状态上报，快速定位到一批因为Flash空间不足而升级失败的设备。

// 示例：在STM32应用程序中，管理OTA状态的简化数据结构
typedef struct {
    uint32_t magic;          // 魔数，用于识别结构体有效性，如0x4F544131 ("OTA1")
    uint32_t file_size;      // 待下载固件总大小
    uint32_t downloaded_len; // 已下载长度（用于断点续传）
    uint8_t  status;         // 当前状态
    uint8_t  retry_count;    // 重试次数
    uint32_t crc_or_hash[8]; // 存储校验值（SHA256结果为8个uint32）
} OTA_StatusTypeDef;

// 将这个结构体保存在Flash的固定扇区（如最后一个扇区）
#define OTA_STATUS_SECTOR_ADDR    (0x0801F000) // 假设STM32F407 Flash末尾地址
OTA_StatusTypeDef *pOTAStatus = (OTA_StatusTypeDef*)OTA_STATUS_SECTOR_ADDR;

常见误区

  • 忽略内存管理：使用Wi-Fi模块的AT指令接收数据时，如果没有足够的环形缓冲区或及时读取，会导致数据包丢失。务必根据模块的吞吐量（如ESP8266单包最大约2KB）设计足够大的缓冲区。
  • 升级过程断电变砖：如果在Bootloader正在擦写应用程序区时断电，设备将无法启动。必须实现双备份或恢复机制。一个简单策略是：Bootloader在开始擦写前，先将旧固件的关键部分（如中断向量表）备份到另一个扇区，如果升级中断，下次启动还能恢复回去。
  • 网络超时设置不当：TCP连接或HTTP请求的超时时间设得太短，在信号弱的场景下容易误判为失败。建议根据网络类型动态调整：Wi-Fi可设为30秒，NB-IoT可能需要2-3分钟。

集成Wi-Fi模块的实战要点

以最常见的ESP8266为例，STM32通过UART发送AT指令控制它连接网络、下载数据。这里有几个踩过的坑。

连接阶段

  • AT+CWJAP指令连接AP后，务必等待“WIFI CONNECTED”和“WIFI GOT IP”两条回复，只收到一条不代表连接成功。
  • 建议保存AP的SSID和密码到Flash，实现自动重连。

传输阶段

  • 使用AT+CIPSTART建立TCP连接到服务器IP和端口。
  • 发送HTTP GET请求时，头部必须包含“Host:”字段，否则某些服务器不响应。
  • 接收数据使用AT+CIPRECVDATA指令（新版本固件），它能指定读取长度，方便管理缓冲区。

稳定性

  • ESP8266工作时发热较大，长期运行在高温环境可能不稳定，要考虑散热。
  • 定期发送AT指令（如AT）进行心跳检测，如果模块无响应，需要硬件复位引脚。
  • 为UART接收中断服务函数加上超时保护，防止因数据异常导致死等。

如果你看到模块一直返回“ERROR”或者根本无响应，大概率是供电不足。ESP8266在发射数据时峰值电流可能超过200mA，确保你的LDO或电源电路能提供至少500mA的电流，并在模块电源引脚就近放置100μF以上的钽电容。

动手试一试

1. 搭建最小测试环境：使用一块STM32F4开发板，通过UART连接一个ESP8266-01S模块。编写代码，让STM32发送AT指令控制ESP8266连接你的手机热点（或路由器）。
2. 实现HTTP GET请求：让ESP8266通过TCP连接到一个公共的测试HTTP服务器（例如 `http://httpbin.org/get`），并接收服务器返回的响应头和数据，将数据通过串口打印出来。
3. 模拟固件下载：在本地电脑搭建一个简单的HTTP文件服务器（用Python的 `http.server` 模块即可），放置一个小的二进制文件（比如一个1KB的`.bin`文件）。修改STM32程序，控制ESP8266从你的本地服务器下载这个文件，并将接收到的数据长度和校验和计算出来，与源文件对比。

这个练习能让你熟悉无线模块的控制、TCP通信和数据处理的基本流程，是迈向完整OTA的第一步。

本章小结

  • 无线OTA升级是一个“云端-通信-设备端”协同的系统工程，设备端负责下载、校验和触发Bootloader。
  • Wi-Fi、4G、NB-IoT等无线方案各有适用场景，需根据速率、功耗、成本和覆盖范围综合选型，差分升级是低速网络下的重要优化手段。
  • 可靠的OTA流程必须包含独立缓存、完整校验、状态管理和断点续传机制，以防止升级过程中因网络或电源问题导致设备变砖。
  • 集成具体无线模块（如ESP8266）时，需特别注意供电稳定性、AT指令交互的健壮性和数据缓冲区的设计。
  • 通过状态上报，可以在云端实时监控大量设备的升级进度和结果，实现高效的远程运维。
